# 05 — Diagrams in the Editor: vendoring, drawing, placement

Status: done
Spec: ../spec.md
Blocked by: 01

## What

Mermaid arrives in the repository, and the Editor's read pane draws a Diagram
with it. This is where the placement that keeps the CSP narrow (ADR-0016) is
written and proved; 06 puts the same placement on the public page.

## Scope

- **Vendoring.** `shared/mermaid.min.js` — the current Mermaid 11 release,
  pinned, the classic (non-module) build so it loads from `file://` — with
  `shared/mermaid.LICENSE`. Its version is in a first-line comment.
- **`bin/build`** copies it to `editor/mermaid.min.js` and
  `site/public/mermaid.min.js`; its header comment lists the two new outputs.
  `bin/test`'s drift check covers both, and the probe's repathing resolves the
  Editor's copy from `tests/`.
- **Loading.** `editor/ui.js` adds one `<script src="mermaid.min.js">` the first
  time a render finds a Diagram, and never on a Document without one.
- **Configuration.** `startOnLoad: false`, `securityLevel: 'strict'`, the
  `base` theme with variables read from the page's CSS custom properties, the
  page's font family.
- **Placement**, written as one function the page can share in spirit with 06:
  `mermaid.render()` → string → `DOMParser` → each `<style>`'s text into one
  `<style>` carrying the nonce, when there is one → each `style` attribute
  into the element's CSSOM → the cleaned SVG replaces the `<pre>`. The copy
  button stays and copies the source.
- **Failure.** `render()` throwing leaves the code block and prints Mermaid's
  message under it, in the read pane.
- **Theme.** `T` redraws every Diagram in the read pane.
- **`bin/test`'s Editor network scan** keeps scanning `editor.js` and `ui.js`
  and does not scan the vendored file; its comment says why. The claim in
  `ui.js`'s header is updated to the one in CONTEXT.md's **Editor** entry.

## Stop condition

If Mermaid needs `'unsafe-eval'`, or any `style` attribute survives placement,
stop and bring it back to grilling. ADR-0016's rejected alternative is not
taken without a decision.

## Out

The public page, which is 06. Drawing in the write pane. Any change to
`renderDoc` — a Diagram's HTML is a code block's HTML.

- 2026-09-30, agent: the stop condition, checked in headless Chromium on a
  page served with `script-src 'nonce-…'; style-src 'nonce-…'` before any of
  the Editor was written:
  - **No `'unsafe-eval'`.** The library's only `Function(…)` calls are
    lodash's `Function("return this")()` global-object fallback, behind
    `typeof self == "object"`, which a browser never reaches. It drew with no
    eval violation.
  - **Style attributes.** Mermaid emits a lot of them: 35 on a nine-line
    flowchart, most not empty (stroke widths, dash arrays, the label `<div>`s'
    layout, and whatever a `style X fill:…` statement says). The placement
    strips every one from the parsed tree and none survives into the page. But
    writing them back through `el.style`, as ADR-0016 says, *is* setting the
    `style` attribute: the CSSOM declaration block and the attribute are the
    same thing. CSP permits it and reports nothing, but the acceptance line
    "no element in the placed SVG has a `style` attribute" cannot hold with the
    ADR's own mechanism. This was brought back as the stop condition asks, and
    the answer was to keep the CSSOM and reword the test. The probe now
    watches the read pane with a `MutationObserver` and asserts that every
    `style` attribute on the placed SVG was *written* after placement, from
    no attribute at all. Moving the CSSOM step before insertion, or dropping
    it, turns that test red (tried both).
- 2026-09-30, agent: for **06**, from the same experiment: under the
  policy, `mermaid.render()` itself logs style-src violations: about 50 on
  that flowchart, from the scratch element it draws in inside the live
  document. Parsing its output with `DOMParser` logs about 36 more (one per
  `style` attribute and `<style>` element), because a parsed document
  inherits the page's policy. The drawing is still right, because the
  placement carries the styles. So 06's "no CSP violation in the console" by
  hand will not hold as written; it is about the console, not the boundary.

- 2026-09-30, agent: choices made where the issue left room:
  - The library is asked for from beside `ui.js` (`document.currentScript`),
    not beside the page. So the probe, which loads `../editor/ui.js`, gets
    the Editor's copy without another rewrite in `bin/build`.
  - The SVG is parsed as `text/html`, not `image/svg+xml`: Mermaid serialises
    its labels as HTML (`<br>`), which is not well-formed XML.
  - Each Diagram is drawn once per source and theme and kept (the 32 most
    recently used), because the read pane is rebuilt on every keystroke. A
    redraw puts the picture straight back with no flash of source, and `T`
    keeps the old picture until the new one is ready.
  - Theme variables: `background`, `primaryColor` and `edgeLabelBackground`
    from `--bg`, text and lines from `--fg`, borders from `--accent`, and
    `darkMode` from the theme. `suppressErrorRendering: true`, because
    without it a failed render leaves Mermaid's error picture in `<body>`,
    and the probe checks for that.
  - A drawn Diagram's copy button copies the exact source. The ordinary code
    block copy, in `ui.js` and in `Page.php` alike, strips one leading space
    from every line (`replace(/^ /gm, '')`, which is meant for the CLI
    prompt), so an indented code block loses a column when copied. That is
    older than this issue and was left alone.
- 2026-09-30, agent: after the two-axis review. Corrected: the scan comment
  in `bin/test` no longer says the page opens no connection itself, since
  `ui.js` now adds a `<script>`. A library that loads but defines no
  `mermaid` now says so on the status line, as a failed load does. Left as
  they are, and why:
  - The placement writes the CSSOM *after* the SVG replaces the `<pre>`. The

  - Two identical Diagrams in one Document share one drawing, so their SVG
    ids repeat. The content is identical, so markers still resolve to the

  - The frame for a drawn Diagram is in `shared/theme.css`, so it already
